Специфікація: Mosslight — пригодницька гра для термінала на Rust

Твоя роль — реалізувати завершену однокористувацьку гру, яку можна зібрати й запустити на macOS та Linux, зокрема на віддаленому сервері через SSH.

Працюй автономно: ухвалюй дрібні рішення самостійно, реалізовуй поетапно та перевіряй результат. Не зупиняйся після каркаса, плану або демонстраційної кімнати.

**1. Концепція**

Mosslight — пригода з видом згори, натхненна структурою та відчуттям Zelda епохи Game Boy:

- компактний світ із переходами між окремими екранами;
- дослідження, секрети, короткі діалоги;
- бої мечем у реальному часі;
- предмет, який відкриває нові маршрути;
- підземелля з ключами, головоломками та фінальним босом.

Створи власні назви, світ, персонажів і карти. Не використовуй персонажів, тексти, музику або карти Nintendo.

Зав’язка: згасло світло лісового маяка. Герой має знайти стародавню жарину в затопленому святилищі та відновити маяк.

Цільова тривалість першого проходження — 30–45 хвилин.

**2. Межі першої версії**

Обов’язковий контент:

| Елемент | Обсяг |
|---|---|
| Зовнішній світ | 9 кімнат, сітка 3×3 |
| Підземелля | 6 кімнат, включно з ареною боса |
| NPC | 3 персонажі |
| Звичайні вороги | 3 типи |
| Бос | 1, дві фази |
| Спорядження | Меч і ліхтар |
| Головоломки | Натискні плити з блоками; запалювання смолоскипів |
| Секрети | Щонайменше 3 |
| Здоров’я | 3 серця спочатку, максимум 5 |
| Збереження | Один слот, автозбереження та ручне збереження |

Не включати в першу версію: процедурну генерацію, мультиплеєр, крафтинг, дерево навичок, магазини, аудіо, редактор карт, підтримку Windows.

**3. Платформи та запуск**

Обов’язкові середовища:

- macOS: Apple Silicon та Intel;
- Linux: x86_64 та aarch64;
- локальний термінал;
- інтерактивний SSH-сеанс із виділеним PTY;
- tmux і screen у сумісному терміналі.

Гра працює повністю на машині, де запущено процес. SSH лише передає клавіатурне введення та термінальний вивід.

Приклади запуску:

```sh
cargo run --release
mosslight
mosslight --ascii --color never --fps 10
ssh -t user@host 'mosslight --ascii --fps 10'
```

Після встановлення гра не потребує інтернету, графічного сервера, браузера, спеціальних шрифтів або зовнішніх файлів ресурсів.

Перевіряти, що stdin і stdout підключені до термінала. Для відсутнього TTY або TERM=dumb завершуватися з коротким поясненням до ввімкнення raw mode.

**4. Вигляд**

Візуальна мета — маленька портативна пригода, а не панель системного моніторингу.

- Фіксована кімната: 24×16 ігрових тайлів.
- Один тайл займає дві колонки та один рядок термінала.
- Мінімальний розмір термінала: 60×24.
- На великих терміналах центрувати сцену.
- Верхня смуга: здоров’я, активний предмет, кількість ключів.
- Центр: поточна кімната.
- Низ: повідомлення та коротка підказка керування.
- Діалоги показувати в окремому вікні з явним переходом далі.

Основна тема — чотири відтінки зеленого. Передбачити палітру ANSI 16 кольорів і повноцінний монохромний режим. Колір не може бути єдиним способом відрізнити об’єкти.

Базовий режим використовує ASCII. Unicode — необов’язкове покращення, тільки символи з перевіреною шириною. Не використовувати emoji, Nerd Fonts, Sixel, Kitty graphics або зображення.

Приклад позначень; кожне доповнюється до ширини тайла:

| Об’єкт | Символ |
|---|---|
| Герой | `@` |
| Стіна | `#` |
| Підлога | `.` |
| Вода | `~` |
| Кущ | `"` |
| NPC | `N` |
| Слиз | `s` |
| Кажан | `b` |
| Вартовий | `g` |
| Скриня | `C` |
| Замкнені двері | `+` |
| Рухомий блок | `O` |
| Натискна плита | `_` |
| Смолоскип | `t` |

Передбачити коротку анімацію удару та помітні сигнали небезпечних атак. Уникати постійного мерехтіння й декоративних анімацій, які створюють зайвий трафік через SSH.

**5. Керування**

| Дія | Клавіші |
|---|---|
| Рух | Стрілки або WASD |
| Удар мечем | J або Space |
| Використати ліхтар | K |
| Взаємодія / підтвердити | E або Enter |
| Карта | M |
| Інвентар | I |
| Пауза / назад | Esc |
| Довідка | ? |
| Вихід із підтвердженням | Q |

Рух — по чотирьох напрямках, без діагоналі. Спроба руху змінює напрямок погляду навіть тоді, коли попереду стіна.

Критична вимога для SSH: не покладатися на події відпускання клавіш, одночасне натискання або розширені клавіатурні протоколи.

Одна отримана подія руху означає один крок за умови завершення затримки між кроками. Системний автоповтор може давати наступні кроки, але гра залишається повністю керованою окремими натисканнями.

Не накопичувати довгу чергу рухів. Після зависання або пакетного надходження введення герой не повинен виконувати десятки старих команд. Обробку введення обмежувати за кількістю подій на ітерацію; надлишкові рухи згортати.

Після закриття меню або діалогу очищати відкладені ігрові команди.

**6. Ігрові механіки**

Рух і зіткнення:

- позиції об’єктів задаються цілими координатами тайлів;
- стіни, вода, зачинені двері та тверді об’єкти блокують рух;
- вихід через визначений прохід переносить у сусідню кімнату;
- після переходу герой з’являється у безпечному тайлі;
- одночасні спроби зайняти один тайл вирішуються детерміновано.

Бій:

- меч уражає один тайл перед героєм;
- одна атака завдає шкоди кожній цілі максимум один раз;
- контакт із ворогом або його атакою забирає здоров’я;
- після отримання шкоди герой має короткий період невразливості;
- відкидання, якщо застосовується, не проходить крізь перешкоди;
- смерть відкриває екран із повторною спробою від останнього збереження.

Початкові значення для налаштування:

| Параметр | Значення |
|---|---|
| Інтервал кроку героя | 120 мс |
| Перезарядження меча | 300 мс |
| Активна фаза удару | 100 мс |
| Невразливість після шкоди | 800 мс |
| Типова шкода | Половина серця |
| Попередження про сильну атаку | Щонайменше 600 мс |

Усі бойові значення тримати в одному місці. Здоров’я зберігати цілими одиницями півсерця.

Вороги:

- Слиз: повільно пересувається, переслідує героя поблизу.
- Кажан: рухається швидше, чергує короткі переміщення та паузи.
- Вартовий: патрулює, попереджає про атаку, виконує ривок і відновлюється.

Створити читабельні автомати станів. Для навігації достатньо простого пошуку шляху по поточній кімнаті або локального руху, якщо вороги не застрягають.

Ліхтар:

- знаходиться в зовнішньому світі;
- активує смолоскип у тайлі перед героєм;
- відкриває позначені приховані проходи;
- не витрачає паливо;
- потрібний для входу в підземелля та головоломки всередині.

Головоломки:

- пересунути блок на плиту;
- запалити кілька смолоскипів за підказкою;
- кожна головоломка має зрозумілий візуальний зворотний зв’язок;
- помилка не створює незворотного блокування проходження;
- вихід і повторний вхід скидає нерозв’язану головоломку;
- розв’язані головоломки зберігають результат.

Бос:

- дві фази з різними шаблонами атак;
- явний сигнал перед небезпечною дією;
- вікно вразливості після атаки;
- відсутність вимог до покадрової точності;
- після перемоги видається жарина;
- повернення до маяка й взаємодія завершують гру.

**7. Світ і прогрес**

Основний маршрут:

1. Почати біля згаслого маяка.
2. Через NPC дізнатися про святилище.
3. Дослідити ліс і знайти меч.
4. Розв’язати просту головоломку та отримати ліхтар.
5. Відкрити вхід у підземелля.
6. Знайти ключі та пройти дві головоломки.
7. Перемогти боса.
8. Повернути жарину до маяка.

Перша безпечна ділянка має навчити руху й взаємодії; наступна — атаці; лише після цього додати складніші загрози.

Карта показує відвідані кімнати, поточне місце та відкриті важливі об’єкти. Невідвідані кімнати приховані.

Опис світу зберігати в читабельному RON або JSON і вбудовувати в бінарний файл під час збирання. Використовувати стабільні ID кімнат, дверей, скринь і сюжетних подій.

Валідатор контенту має перевіряти:

- розміри карт і допустимі тайли;
- унікальність ID;
- існування цілей переходів;
- коректність точок появи;
- взаємність двосторонніх переходів;
- доступність потрібних ключів до відповідних замків;
- наявність прохідного основного маршруту.

**8. Технічна архітектура**

Мова: Rust stable. Зафіксувати перевірений toolchain і Cargo.lock.

Бібліотеки:

- ratatui — рендеринг;
- crossterm — введення й керування терміналом;
- serde та RON або JSON — контент і збереження;
- clap — CLI;
- додаткові невеликі бібліотеки лише за конкретної потреби.

Узгодити версії Ratatui та Crossterm, щоб уникнути несумісних типів подій.

Не використовувати ігровий рушій, асинхронний runtime або повноцінну ECS без обґрунтованої потреби. Для цього обсягу достатньо одного потоку, структур, enum і колекцій сутностей.

Рекомендована структура:

```text
src/
  main.rs
  app.rs
  terminal.rs
  input.rs
  render/
  game/
    state.rs
    world.rs
    entities.rs
    combat.rs
    ai.rs
    puzzles.rs
  content/
  save.rs
  config.rs
assets/
  world.ron
tests/
```

Головна вимога: симуляція не залежить від термінала.

Орієнтовний інтерфейс:

```rust
fn update(
    state: &mut GameState,
    actions: &[Action],
    dt: Duration,
) -> Vec<GameEvent>;
```

Рендеринг лише читає стан. Введення перетворюється на семантичні Action. Випадковість, якщо потрібна, має керований seed.

Не читати системний час усередині бойових правил та AI; передавати час через симуляцію.

**9. Ігровий цикл і SSH**

- Фіксована частота симуляції: 30 оновлень/с.
- Максимальна частота рендерингу: 20 кадрів/с за замовчуванням.
- Параметр `--fps` обмежує лише рендеринг.
- У паузі та статичних меню перемальовувати лише за зміни стану.
- Використовувати диференційне оновлення екрана.
- Не очищати весь екран на кожному кадрі.
- Не використовувати активне очікування.
- За великої затримки виконувати максимум 5 наздоганяльних кроків і відкидати надлишковий накопичений час.
- Меню, карта, інвентар і діалоги призупиняють симуляцію.

За надто малого розміру термінала призупинити гру, показати потрібний і поточний розмір. Після відновлення розміру відкрити паузу, щоб герой не отримав несподівану шкоду.

Не намагатися визначати факт обриву SSH за відсутністю натискань. Якщо гра має продовжувати існувати після розриву з’єднання, користувач запускає її в tmux або screen.

**10. Збереження**

Зберігати:

- версію формату;
- безпечну позицію героя;
- здоров’я та максимальне здоров’я;
- спорядження й ключі;
- відвідані кімнати;
- відкриті скрині та двері;
- розв’язані головоломки;
- сюжетні прапорці та перемогу над босом.

Не зберігати активну анімацію атаки або проміжний стан звичайного бою. Після завантаження вороги відновлюються; герой має короткий безпечний період. Бій із босом починається заново з входу на арену.

Автозбереження: після безпечного переходу, отримання важливого предмета, розв’язання головоломки та перемоги над босом. Ручне збереження — через меню поза боєм.

Заборонити запис стану смерті поверх останнього придатного збереження.

Шлях:

- Linux: `$XDG_DATA_HOME/mosslight`, за відсутності — `~/.local/share/mosslight`;
- macOS: `~/Library/Application Support/mosslight`;
- `--save-dir` перевизначає каталог.

Записувати через тимчасовий файл у тому самому каталозі та атомарне перейменування. Зберігати попередню валідну копію.

Пошкоджений файл не повинен спричиняти panic або мовчки перезаписуватися. Запропонувати відновлення резервної копії або нову гру. Невідому новішу версію формату не перезаписувати.

**11. Надійність термінала**

Використати guard для життєвого циклу термінала та panic hook.

Після нормального виходу, обробленої помилки й unwind panic потрібно:

- вимкнути raw mode;
- залишити alternate screen;
- показати курсор;
- відновити стилі;
- лише після цього друкувати діагностику.

Обробляти Ctrl+C як запит на коректне завершення. SIGTERM і SIGHUP передавати в основний цикл через безпечний механізм сигналів; не виконувати файлові операції в signal handler.

Врахувати помилки запису після обриву SSH. Відновлення термінала виконувати в межах доступного з’єднання.

SIGKILL і аварійне вимкнення живлення не дають гарантій cleanup; захист даних забезпечується атомарними збереженнями.

Логи не виводити поверх гри: використовувати окремий файл або показувати помилки після виходу з TUI.

**12. CLI**

```text
mosslight
  --ascii
  --unicode
  --color auto|always|never
  --theme gameboy|ansi|mono
  --fps 10|20|30
  --save-dir PATH
  --seed NUMBER
  --help
  --version
```

За замовчуванням — ASCII, тема gameboy із доступним кольоровим fallback, 20 FPS. Поважати NO_COLOR; явний `--color` має пріоритет.

У головному меню: Continue, New Game, Help, Quit. Перезапис наявного проходження через New Game потребує підтвердження.

**13. Перевірки**

Обов’язкові автоматичні перевірки:

- рух і зіткнення;
- переходи між кімнатами;
- напрямок та зона удару;
- перезарядження й невразливість;
- двері споживають ключ лише один раз;
- головоломки та їх скидання;
- смерть і відновлення;
- обидві фази боса та фінальна перемога;
- round-trip збереження;
- пошкоджений і несумісний save;
- валідність контенту;
- однакова симуляція за однакового seed та послідовності дій.

Додати headless-сценарій проходження від початку до перемоги через звичайні ігрові дії, без прямого виставлення сюжетних прапорців.

Використати тестовий backend для перевірки розміщення сцени, ASCII-режиму й повідомлення про малий термінал.

Команди готовності:

```sh
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --locked
cargo build --release --locked
```

Ручна перевірка:

- локальний запуск на macOS і Linux;
- запуск через SSH із PTY;
- tmux;
- 60×24 та 80×24;
- зміна розміру під час гри;
- монохромний режим;
- затиснута клавіша без накопичення довгого руху;
- збереження, вихід і продовження;
- коректний термінал після виходу та контрольованого panic.

Перевірити керованість за приблизно 150 мс RTT, якщо середовище дозволяє. Виміряти процесорне навантаження й обсяг термінального виводу за хвилину гри та паузи, зазначивши середовище.

Не стверджувати, що платформа або сценарій перевірені, якщо їх фактично не запускали.

**14. Порядок реалізації**

1. Термінальний цикл, меню, одна кімната, рух, resize і cleanup.
2. Бій із одним ворогом і повний короткий ігровий цикл.
3. Кімнати світу, переходи, NPC та предмети.
4. Підземелля, головоломки, бос і завершення.
5. Збереження, CLI, палітри й SSH-перевірки.
6. Баланс, автоматичне проходження, документація.

Після кожного етапу має залишатися робоча збірка. На завершення не залишати заглушок у головному маршруті.

**15. Результат і критерії приймання**

Передати:

- повний Rust-проєкт;
- вбудовані карти й контент;
- Cargo.lock і зафіксований toolchain;
- README зі збиранням, керуванням і запуском через SSH;
- короткий опис архітектури;
- тести та CI для Linux і macOS;
- звіт про виконані перевірки й відомі обмеження.

Готово, коли:

- гру можна пройти від меню до фіналу;
- доступні всі 15 кімнат і передбачений контент;
- головний маршрут не має тупиків через ключі чи головоломки;
- керування працює без key-release та спеціальних протоколів;
- ASCII й монохромний режими залишаються повністю зрозумілими;
- частота рендерингу не змінює швидкість симуляції;
- збереження відновлює прогрес;
- штатний вихід повертає термінал у придатний стан;
- перевірки проходять, а неперевірені середовища чесно позначені.

Почни з перевірки репозиторію та короткого плану, після чого одразу реалізовуй.
