## [MINOR] The corrupt-save `detail` and `path` are captured and then thrown away
`src/app.rs`

`LoadOutcome::Corrupt { path, detail }` exists specifically to carry a diagnostic (ADR 0006 names it), but `SlotState::from` at src/app.rs:48 drops `path` (`..`) and stores `detail` into `SlotState::Corrupt { detail }` — and `grep detail src/` confirms that field is never read anywhere. `draw_save_problem` shows only the title "Save damaged"; nothing is pushed into `self.diagnostics`, so nothing reaches stderr after the guard drops. A player or a maintainer whose save went bad has the serde error message and the file path already in hand at src/save.rs:436-472 and loses both. Same for the two `RestoreError` arms at src/app.rs:266-281, which synthesize a `detail` string that is likewise never surfaced. The `App` diagnostics channel already exists and is drained by `main` (src/main.rs:183-185), so this is a one-line gap, not a design one.

**Fix:** In `App::new`, after the `io.load()` probe, push a line into `diagnostics` when the outcome is `Corrupt` — e.g. `format!("save: {} is damaged: {detail}", path.display())` — and do the same in `restore_backup`'s `Corrupt` arm and in `try_restore`'s two `RestoreError` arms. Keep `path` on `SlotState::Corrupt` (or log it before discarding it) so the message names the file.

## [MINOR] After a deliberate New Game, `Continue` reports "no save yet" while a real save still sits on disk
`src/app.rs`

The r1 minor-#2 fix makes `start_new_game()` (src/app.rs:231-234) clear a `Usable` slot to `Empty`, but nothing deletes `save.json`. Sequence: main menu → New Game over a usable slot → ConfirmNewGame → Confirm (slot becomes `Empty`, fresh run) → die before the fresh run's first autosave → GameOver → `Cancel` → MainMenu. `continue_label()` now returns "Continue (no save yet)" and selecting Continue prints "No save yet", even though the abandoned run is intact on disk and would load fine. The player who changed their mind has no in-session way back to it — only restarting the process re-probes the slot. Secondarily, `new_game_from_menu` now takes the `Empty` branch, so a second New Game starts with no §12 overwrite confirmation, and its first autosave overwrites the on-disk save without a second ask. The window is narrow (one room transition closes it) and the player did consent once, but the menu is actively misreporting disk state, which is the thing `SlotState` exists to describe.

**Fix:** Keep `self.slot` describing what is actually on disk, and express "this fresh run must not retry into the old save" as its own flag instead: add e.g. `retry_target: Option<Box<SaveFile>>` (or a `run_is_fresh: bool`) that `start_new_game()` clears and every successful `store` sets, and have `apply_game_over`'s `Confirm` arm consult that rather than `self.slot`. `continue_label`, `new_game_from_menu` and `save_problem_items` then keep reporting the truth. `tests/save.rs::retry_before_first_autosave_after_a_deliberate_new_game_never_resurrects_the_abandoned_run` should keep passing unchanged apart from its `SlotState::Empty` assertion.
