# Review — phase 2 round 2

**Verdict:** approve

Round 2 clears both round-1 majors and every minor, and I verified the two majors by reproducing the original defects against the rebuilt binary: a walled-in arrival spawn in the real world.ron is now rejected with `DoorUnreachableInRoom`, and a misspelled field name is a parse error. The fix for reachability is the right one — a full `(room, tile-connectivity-component)` state in the `(unlocked, items)` BFS, not the weaker static heuristic the round-1 review sketched (DECISIONS.md explains why the sketch was unsound, which is a better answer than the one it was given). `App::new` now takes the already-validated `Rc<World>`, so the content path has no unwrap-family call and `--debug-content` plays what it validated; the every-door test now checks the grid geometry rather than just the engine honouring a declaration; `first_visit` is asserted in both polarities; `Progress` no longer serializes dense indices. All seven acceptance criteria have a named test, all 14 PLAN tasks are `[x]` with code behind them, the ARCHITECTURE deviations are all logged, and the full gate passes locally (fmt, clippy `-D warnings`, 116 tests). The two remaining findings are both `minor` and both about validator surface phases 4–5 will lean on: object positions (chests/NPCs/enemies) are never position-checked, and seven error rules have no test that makes them fire. Neither blocks the phase.

## [MINOR] Chest, NPC, enemy and puzzle positions are never bounds- or walkability-checked
`src/content/validate.rs`

`check_spawns` only iterates `room.spawns`. Nothing anywhere validates `Chest.at`, `Npc.at`, `EnemySpawn.at` or an `EnemySpawn.patrol` waypoint. A chest authored at (99, 99) or inside a `Wall` parses and validates clean: `compute_components` simply returns `None` for the tile, so the chest is dropped out of the reachability search without a word. Today that is caught indirectly only for `Reward::SmallKey` (surfaces as `LockNeverUnlockable`) and `Reward::Ember` (surfaces as `EmberUnreachable`); a walled-in `chest.forest_sword`, `HeartContainer` or `Message` chest, or an enemy spawned out of bounds, produces no error at all. Spec §7's "коректність точок появи" reads naturally as covering enemy spawn points too, and the phase goal is explicitly to make completability machine-checked *before any content is authored* — phase 4 authors exactly these objects. `.autodev/RISKS.md` #1 names "a spawn inside a wall" as the headline failure class.

**Fix:** Extend `check_spawns` (or add a `check_object_positions`) to run the same in-bounds test over every `chest.at`, `npc.at`, `enemy.at` and patrol waypoint, reusing `ContentError::PositionOutOfBounds { what: format!("chest '{id}'") }`. For chests, also assert the tile is walkable (or, if phase 4 decides chests occupy a solid tile, that at least one orthogonal neighbour is), and add a fixture with a chest in a wall.

## [MINOR] Seven ContentError rules are never made to fire by any test
`tests/content.rs`

`UnknownSpawn`, `PositionOutOfBounds`, `SpawnOnDoorTile`, `DoorTileMismatch`, `DuplicateMapIndex`, `HomeUnreachableWithEmber` and `EmberMissing` appear only in `error.rs`'s `all_variants()` Display test — no fixture, in-module test or integration test ever drives the validator into producing them. That is the same hole the phase's own second acceptance criterion exists to close ("a validator that silently passes everything cannot make the suite green"), just for the rules the criterion does not enumerate. `HomeUnreachableWithEmber` and `EmberMissing` matter most: they are the §15 main-route rules that stay dormant until phase 5 flips `route.ember_required` to `true`, so a defect in them would be discovered at the exact moment the run can least afford it. (I read both; they look correct — the point is that nothing would tell you if they weren't.)

**Fix:** Add three cheap fixtures derived from `base.ron` — one moving a spawn onto its door tile (`SpawnOnDoorTile`), one giving `room.b` `room.a`'s `map_index` (`DuplicateMapIndex`), one deleting `chest.ember` while `ember_required: true` stays (`EmberMissing`) — plus an in-module `validate.rs` test for `HomeUnreachableWithEmber` (a one-way door into the ember room). `UnknownSpawn`/`PositionOutOfBounds`/`DoorTileMismatch` are one-line mutations of the existing fixtures.
